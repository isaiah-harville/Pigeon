# Pigeon v1.2 Hardening Design

## Release boundary

Pigeon v1.2 is a hardening release with five independently reviewable changes:

1. Crash-consistent messaging.
2. Explicit encrypted-store recovery.
3. Relay protocol compatibility negotiation.
4. Redacted diagnostics.
5. Reproducible release tooling and warning cleanup.

Clean-slate/Faraday controls and traffic-analysis resistance remain separate work.

## Security and failure model

Transports and relays are untrusted and may replay, delay, drop, or inject bytes.
The local file system may be unavailable, full, corrupted, or interrupted during a
write. Pigeon must not acknowledge custody of a relay envelope or advance a peer's
delivery state unless the corresponding message and ratchet state are durable.
Failures must not silently reset identity, contacts, conversations, or sessions.

## Crash-consistent messaging

Inbound processing returns a disposition to its transport: consumed only after a
valid envelope is either durably handled or intentionally ignored as irrelevant;
retry when locked, storage fails, or handling cannot safely complete. Relay mailbox
acknowledgements are sent only for consumed envelopes. For application messages,
decrypt, deduplicate, record, and persist before encrypting the end-to-end delivery
ack. A persistence failure disables further session mutation for the run and leaves
the relay copy unacknowledged. Outbound/session-control ciphertext is emitted only
after the advanced session pickle is durably saved.

## Storage recovery

Encrypted-store load distinguishes missing, loaded, inaccessible, corrupted, and
wrong-key/undecryptable states. Store location discovery is fallible and never uses
the temporary directory. Unlock presents a blocking recovery state for anything
except missing or loaded data. Existing split bulk/crypto files remain the v1.2
format; a broader unified-store migration is deferred because it would enlarge the
failure surface of this release.

## Relay compatibility

The relay protocol has an integer compatibility version independent of component
SemVer. Client and relay exchange inclusive minimum/maximum ranges before any
publish, subscribe, authentication, or push registration. They select the highest
overlap. Missing, malformed, or non-overlapping ranges fail closed. Incompatible
relays remain visible only in settings as incompatible; they never become ready,
carry traffic, affect reachability, or appear in newly generated contact cards.

## Diagnostics

Runtime diagnostics use a small typed event vocabulary rendered without contact
names, identity/fingerprint fragments, transient peer identifiers, relay hosts,
payload sizes, or plaintext-adjacent error descriptions. User-facing status remains
actionable. Release builds do not retain detailed transport activity.

## Release integrity

The relay image builds from the repository root with the workspace `Cargo.lock` and
`--locked`. Obsolete member lockfiles are removed. CI formatting excludes generated
bindings and treats handwritten warnings as failures. Redundant handwritten
`Sendable` conformances are removed. Version-validation paths cover every changed
deployable component.

## Verification

Each PR adds focused regression tests first, then runs its narrow suite plus the
affected Rust/Swift/iOS build checks. Security-sensitive PRs include failure-path
tests, not only successful round trips.
